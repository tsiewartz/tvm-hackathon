Semantic view in dbt

The semantic view is where your business logic lives: what the tables mean, how they join and how each metric is calculated. Answer quality depends on it more than on anything else you build today.

How it works in dbt

Your project has a small custom materialization, semantic_view_yaml. The model body is the semantic view's YAML, the same format Semantic Studio shows and exports. dbt fills in the table names with source() and creates the view with SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML. The view is named after the model: SV_TEAM_{{N}}.

You start from the skeleton in the golden path. A grown-up version looks like this (tested on our account):

-- {{FOLDER}}/sv_team_{{N}}.sql
{{ config(materialized='semantic_view_yaml') }}
description: 'Subscriber base and MRR per month, by plan. For the TVM subscription team.'
tables:
  - name: MART
    description: 'One subscriber per month the subscription was live'
    base_table: {{ base_table(source('tvm_marts', 'fct_subscriber_months')) }}
    dimensions:
      - name: PERIOD
        description: 'First day of the calendar month'
        expr: mart.month_start
      - name: PLAN_ID
        expr: mart.plan_id
    facts:
      - name: AMOUNT
        description: 'Monthly recurring revenue in EUR, excl. VAT'
        expr: mart.mrr_eur
    metrics:
      - name: TOTAL_AMOUNT
        description: 'Total MRR in EUR'
        expr: SUM(mart.amount)
  - name: PLANS
    description: 'One row per subscription plan'
    base_table: {{ base_table(source('tvm_marts', 'dim_plans')) }}
    primary_key:
      columns: [plan_id]
    dimensions:
      - name: PLAN_NAME
        description: 'Plan name as shown to customers'
        expr: plans.plan_name
relationships:
  - name: mart_to_plans
    left_table: MART
    right_table: PLANS
    relationship_columns:
      - left_column: plan_id
        right_column: plan_id
module_custom_instructions:
  sql_generation: 'If no period is given, use the last 12 complete months and say which months.'
  question_categorization: 'Decline questions about individual subscribers.'
verified_queries:
  - name: amount_per_month
    question: 'What was the total amount per month?'
    use_as_onboarding_question: true
    sql: |
      SELECT period, SUM(amount) AS total_amount FROM mart GROUP BY period ORDER BY period

Build (driver), then check it:

SELECT * FROM SEMANTIC_VIEW({{DEV_DB}}.{{SCHEMA}}.SV_TEAM_{{N}}
  METRICS mart.total_amount DIMENSIONS plans.plan_name);
How the parts fitexpr on a dimension or fact points at a column (mart.month_start). A metric aggregates a fact (SUM(mart.amount)). Verified-query SQL uses the logical names (FROM mart, period, amount), not the real table.

Build it in the UI, keep it in dbt

You don't have to write the semantic view by hand. Snowsight's Semantic View Autopilot and Semantic Studio suggest descriptions, keys, relationships and verified queries, and let you test questions straight away. This is a good job for the business tester. dbt stays the place where it lives.

Export before anyone buildsYou can edit SV_TEAM_{{N}} directly in the UI, and your agent uses the changes right away, so you can test them in CoWork. But the next dbt build replaces the view with what's in the file. So: say it in the team when you edit in the UI, and nobody builds until it's exported and pasted. For a bigger experiment you might throw away, use a copy such as SV_TEAM_{{N}}_DRAFT.
  1. Edit in the UI: open SV_TEAM_{{N}} under AI & ML » Cortex Analyst (it opens in Semantic Studio), or start a new one with Workspaces » Add new » Semantic View in your schema {{SCHEMA}}. Add tables, descriptions and verified queries, and test until your golden questions work.
  2. Export it as a dbt model: in the bottom panel, command Run operation, with flags:
export_yaml --args "{name: {{DEV_DB}}.{{SCHEMA}}.SV_TEAM_{{N}}}"
  1. Paste: copy everything between the ----- paste and ----- end lines in the output into {{FOLDER}}/sv_team_{{N}}.sql, replacing what's there. The export already uses source('tvm_marts', …) for the mart tables, so dbt lineage stays intact.
  2. Build (driver only). Your agent now uses the improved view.

The pasted model has the same shape as above, with every data_type filled in. Keep editing it in the file or in the UI, as long as you export before the next build:

{{ config(materialized='semantic_view_yaml') }}
description: 'Subscriber base and revenue per month'
tables:
- name: MART
  description: One subscriber per month the subscription was live
  base_table: {{ base_table(source('tvm_marts', 'fct_subscriber_months')) }}
  dimensions:
  - name: PERIOD
    expr: mart.month_start
    data_type: DATE
  metrics:
  - name: TOTAL_MRR
    expr: SUM(mart.mrr_eur)

Best practices

Design and scope

✓ Do

  • Design for the business user: business words, not table names
  • One domain per semantic view, scoped to your track
  • Start with 3–10 tables, ideally a star schema (one fact table plus its dimensions)
  • Include only columns people will actually ask about

✗ Don't

  • Build an "all tables" semantic view
  • Add every column "just in case"
  • Start in a domain that needs near-100% accuracy (e.g. finance reporting)

Descriptions matter most

Snowflake's own guidance calls descriptions the single most important element for accuracy. The model can't guess TVM-specific terms, abbreviations or business rules.

✓ Good

  • description: 'Active subscriber: has a paid, non-cancelled subscription on the last day of the month. Excludes free trials.'

✗ Poor

  • description: 'Active flag'

Metrics, relationships and filters

  • Define every relationship your questions need. The agent won't join tables otherwise. For many-to-many, add a bridge table.
  • Define metrics for every calculation people discuss (rates, averages, distinct counts). That's how "churn" stops meaning three different things.
  • Use derived metrics (a top-level metrics: block, metric over metric) for ratios, and non_additive_dimensions for snapshot measures like balances or subscriber counts.

Synonyms: less is more

Current guidance is to skip synonyms unless a term is internal, an abbreviation or a legacy name the model can't know (e.g. TVM product codes). Auto-generated synonyms often make things worse.

Custom instructions: two kinds

Key under module_custom_instructionsUse forExample
sql_generationBusiness logic applied to every query"If no date filter is given, use the last 12 complete months."
question_categorizationWhen to refuse or ask for clarification"If a question asks about individual users, decline and explain that only aggregates are available."

Be specific, then test after every change.

Verified queries: after the basics

  • Add them once descriptions, relationships and metrics are solid. They optimise a good model; they don't fix a weak one.
  • Start from your golden questions. Mark 2–3 with use_as_onboarding_question: true so users see them as starter questions. Easiest: add and test them in Semantic Studio, then export.
  • SQL uses logical names (FROM mart, period), not the real table and columns. Use sql: | so quotes need no escaping.

Governance and deployment

  • Masking and row access policies on the underlying tables flow through to the semantic view and agent.
  • Sample values are metadata and aren't masked, so never put real PII in them.
  • Each build re-creates the view. Today only your dev role uses it; after today, add grants with a dbt post-hook.
  • Promote dev → prod with your normal dbt CI/CD, or by cloning the schema.

Common errors
  • YAML indentation: two spaces per level, and list items start with - . Most build errors are a misaligned line
  • invalid identifier: a column in expr doesn't exist in the table. Check it under Databases
  • A relationship's right_table needs a primary_key on the join column
  • A metric must aggregate a fact or column (SUM, COUNT, AVG…), and a dimension must not
  • Descriptions go in description: inside the model, not in a schema.yml
