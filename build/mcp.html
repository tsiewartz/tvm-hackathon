MCP + Claude Code

The Model Context Protocol (MCP) is a standard plug between AI assistants and tools. Snowflake hosts the MCP server for you. Your team exposes one tool, your agent, so every client that connects gets the same instructions, guardrails and governed data.

Check first: Claude Code and IT policyOne laptop per team (the agent builder's) needs Claude Code, and TVM's IT policy must allow it and custom MCP servers. If it doesn't, skip this page: the same agent already works in Snowflake CoWork, and that's enough for the demo.
Why expose the agent, not the semantic view?The semantic view is already a tool inside your agent. Exposing only the agent means Claude always goes through your instructions, refusal rules and cost budget. There's one entry point, and no second path that skips them.

Define

An MCP server object (a dbt model) lists the tools to expose.

Authenticate

Claude calls Snowflake over HTTPS with a short-lived token, as your user and role.

Use

Claude discovers the tools and decides when to call them.

The MCP server as a dbt model

You already built it in the golden path: {{FOLDER}}/mcp_team_{{N}}.sql. Update the description once your agent knows what it's for. That's what Claude reads to decide when to call your agent.

{{ config(materialized='mcp_server') }}
tools:
  - name: "team-{{N}}-agent"
    type: "CORTEX_AGENT_RUN"
    identifier: "{{ ref('agent_team_{{N}}') }}"
    title: "Team {{N}} agent"
    description: "Ask business questions about subscriber churn and retention. Returns an answer with the SQL used."
    annotations: { readOnlyHint: true, destructiveHint: false, openWorldHint: false }

Snowflake adds a few helper tools automatically (ASYNC_AGENT_RUN_STATUS, AGENT_RUN_RESULT, ASYNC_AGENT_RUN_CANCEL) so that clients can handle long-running agent calls.

Connect Claude Code (one laptop per team)

One person per team, usually the agent builder, sets this up. That laptop is used for testing and for the demo, so the team needs one token, not three.

1 · Create a token

  1. Snowsight » user menu (bottom left) » Settings » Authentication » Programmatic access tokens » Generate new token.
  2. Role: your dev role. Expires in: 1 day is enough.
  3. Copy the token right away. Snowsight shows it only once.

2 · Check the token and the URL with curl

Your account identifier is in the user menu » Account » View account details. Use hyphens, not underscores.

export SNOWFLAKE_PAT='<token>'          # never paste it into a chat or commit it
export SNOWFLAKE_HOST='<org>-<account>.snowflakecomputing.com'
export MCP_URL="https://$SNOWFLAKE_HOST/api/v2/databases/{{DEV_DB}}/schemas/{{SCHEMA}}/mcp-servers/MCP_TEAM_{{N}}"

curl -s -X POST "$MCP_URL" -H "Authorization: Bearer $SNOWFLAKE_PAT" \
  -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
  • The answer lists team-{{N}}-agent plus the three helper tools

3 · Add it to Claude Code

claude mcp add --transport http team-{{N}} "$MCP_URL" \
  --header "Authorization: Bearer $SNOWFLAKE_PAT"
claude      # then /mcp → team-{{N}}: connected

Then ask it a golden question, e.g. "Use the team-{{N}} agent: what was the total amount per month this year?"

Invalid OAuth access token (HTTP 401)Token wrong or expired, or blocked by the network policy (are you on the TV4 network or VPN?)

Best practices

✓ Do

  • Expose only the agent. It carries your instructions and guardrails
  • Write tool descriptions for the AI client: what's covered and when to use it
  • Mark read-only tools with readOnlyHint: true
  • Use short-lived, role-restricted tokens behind a network policy
  • Grant USAGE on the MCP server to the roles that need it, and nothing more

✗ Don't

  • Add the semantic view or SYSTEM_EXECUTE_SQL as extra MCP tools. They let clients bypass the agent
  • Use an admin role for MCP tokens
  • Pass your token to other people or tools
  • Treat tool annotations as security. They're hints, and access control is what enforces

Production note: for longer-lived use, move from PATs to OAuth for MCP clients.
