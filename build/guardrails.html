Guardrails

An AI agent is only as trustworthy as the controls around it. The good news: in Snowflake, the AI layer inherits your existing governance. Agents and MCP see exactly what the role sees, and no more.

Access

Roles decide what data the agent can reach.

PII

Masking and row access policies flow through to every answer.

Cost

Warehouse limits, monitors and per-answer token budgets.

Quality

Verified queries, evaluation and clear "I don't know" behaviour.

Access

  • Build with your dev role. Give business users a separate consumer role that has USAGE on the agent and MCP server only.
  • Agents using semantic views need SELECT on the semantic view and its underlying tables for the executing role.
  • Manage grants in code: meta.grant_usage_to on agent and MCP models, grants: on tables, and copy_grants=true on semantic views.

PII & sensitive data

✓ Do

  • Leave PII columns out of the semantic view unless the use case truly needs them
  • Rely on masking and row access policies on the base tables. They're enforced through semantic views and agents
  • Attach policies with a dbt post-hook, so they're re-applied on every build
  • Add an AI_QUESTION_CATEGORIZATION rule that declines questions about individuals

✗ Don't

  • Put real PII in sample values. They're metadata and not masked
  • Copy PII into prompts, instructions or verified-query SQL
  • Assume dev data is safe. Check whether it's masked or pseudonymised
-- dbt post-hook: re-apply a policy on every build  (production pattern)
{{ config(post_hook="alter table {{ this }} modify column email set masking policy <GOV_DB>.<GOV_SCHEMA>.MASK_EMAIL") }}

Challenge: prove it

  • Ask the agent for "a list of subscriber emails". It declines or returns masked values
  • Ask an out-of-scope question. It says it can't help, and doesn't invent an answer
  • Stretch: if TVM has a business-user role, check that it can use the agent but can't change it or reach other schemas
  • Check what your team spent today (query below)
SELECT warehouse_name, SUM(credits_used) AS credits
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE start_time >= CURRENT_DATE GROUP BY 1 ORDER BY 2 DESC;   -- can lag up to ~3 h
